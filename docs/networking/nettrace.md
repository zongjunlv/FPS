# 联机战斗链路诊断（临时）

`FPS_NETTRACE=1` 在启动进程时启用 `[NETTRACE-v1]` 日志；默认关闭，不改变射击、AI 或插值逻辑。客户端记录 UDP RTT、世界 Tick 变化、NGO 主线程应用世界状态的间隔、射击提交尝试与反馈、每个敌人的复制位置和表现位置；服务端记录射击 RPC 到达/入队、权威敌人位置与射击结算。诊断日志可能包含玩家和敌人的位置，分享前应确认不含其他敏感内容。

同一战局分别保存客户端与服务端的 Unity Player 日志，然后运行：

```bash
python3 scripts/networking/analyze_nettrace.py \
  --client-log /path/to/client-player.log \
  --server-log /path/to/server-player.log
```

退出码 `0` 表示采样足够且未超过初始告警阈值，**不等于整场对局通关，也不等于玩家完全感受不到延迟**；`1` 表示出现高 RTT、射击反馈超时、世界状态应用停顿、快照不完整或敌人位移异常；`2` 表示样本或跨机轨迹关联证据不足。阈值仅用于排障，不是游戏正式性能指标；可用 `--help` 调整。服务端和客户端应运行同一版本，日志应来自同一场对局。没有服务端日志时可省略 `--server-log`，但无法确认权威敌人轨迹。完整通关还需单独检查对局流程测试结果。

敌人载荷目前没有逐目标快照 Tick；`WorldState.ServerTick` 不是每只敌人位置的精确发送 Tick。`worldApply` 表示 NGO 在客户端主线程应用世界状态，不是 UDP socket 收包时间；同帧多个目标变化也不代表多个网络包。`shotSubmit` 是客户端调用 RPC 前的尝试，不是 UDP 已发出的凭证；`shotReceive` 才表示服务端 RPC 入口已执行，`shot` 表示仿真已结算。服务端拒绝的命令本来不会产生射击反馈，不能误报为反馈丢包。跨机器的 UTC 时间不直接相减求单向延迟。诊断首先依靠客户端本机单调时钟计算射击提交到反馈时间、RTT 和世界状态应用停顿，再结合服务端与客户端的敌人位置序列判断异常首先出现在哪一层。服务端轨迹明显移动而客户端轨迹静止时，若无法证明两份日志在同一时间段重叠，结果为“证据不足”，不能直接归咎于 UDP。

## 本地对照结果（2026-09-26）

隔离构建的静默服务端与双客户端实测：150 ms 往返延迟档完整通关，两名客户端各 20 次射击均获得反馈，RTT p95 分别为 166/168 ms，最慢射击反馈为 192/185 ms；80 ms 往返延迟加 5% 丢包档也完整通关，RTT p95 为 98/99 ms，但世界状态最长约 183/242 ms 未更新、射击反馈最慢约 346/310 ms。这表明稳定延迟不必然导致停发，而丢包会造成可感知的停顿。零延迟档的诊断指标正常，但自动通关脚本在终端交互阶段失败；此流程失败与链路指标应分别处理。这些都是本机模拟网络条件，不能替代腾讯云公网对局的客户端与服务端同场日志。

## 腾讯云公网复现与边界（2026-09-27）

自动化诊断双客户端通过房间服务成功建房、拿到战斗票据，但在当次运行中直连腾讯云 UDP 17777 时，客户端只记录发送，服务端记录的连接数和收包字节均为 0。服务器已绑定 `0.0.0.0:17777`；同一热点绑定 `en0` 后向独立公共 STUN 的真实 IPv4:19302 发包，77 ms 收到有效响应。本机 DNS 仍返回 `198.18.0.0/15` 代理虚拟地址，因此该对照使用服务器解析得到的真实地址。腾讯云上的单独 UDP 443 回显探测也无返回。这些只描述**特定自动化客户端与原始探针**，不能推广到用户的 Unity 编辑器会话：`Editor.log` 另有多次经过 `NetworkManager.IsConnectedClient` 判定的专用服务器连接成功记录，一个已成功连接的真实会话也在服务端记录了双向 UDP 流量。探针失败既不能证明热点/腾讯云 UDP 整体不通，也不能解释已经建立的战斗会话里敌人反馈迟缓；后者必须用同一场次的两端日志追踪。

为隔离游戏逻辑，使用临时 SSH 中继跑过双客户端：两名玩家连接并推进到撤离阶段，但旧版自动验收脚本在撤离集合失败；该次客户端 A 的 RTT p95 为 129 ms、世界状态应用最长间隔为 209 ms、最慢射击反馈为 574 ms。客户端 B 的约 13.6 m 表现偏差发生在故意断线约 10 秒后的同代重连恢复，不是持续性网络漂移。另一次追踪发现某个 Trilobite 的权威根节点在地面，而客户端模型渲染在约 5 m 高处；其 Addressable 模型自带的 `NavMeshAgent` 在客户端继续驱动子物体，和服务端权威位置冲突。

已对重连/长间隔快照采用直接对齐，并禁用客户端表现模型自带的 `NavMeshAgent`、恢复模型预制体局部姿态；自动验收移动改为沿 NavMesh 路径角点前进。这些修复通过 9 个 EditMode 与 8 个 PlayMode 回归测试。**新版本尚未在真实公网 UDP 链路上完成双客户端通关验收**：后续 SSH 中继复测出现秒级乃至十余秒的 TCP 隧道阻塞，不能作为正式 UDP 性能证据。服务器上的临时 `FPS_NETTRACE=1` 已关闭，诊断代码默认不产生日志。
