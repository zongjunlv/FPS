# 客户端与服务端：一晚问答回顾及联机同步改造说明

> 适用范围：FPS 项目的双人 PvE 联机模式。本文区分**当前代码行为**、**今晚观察到的故障**和**下一步设计**；不能把设计方案或本机测试当成公网全流程验收结果。

## 先记住这五句话

1. 账号和房间属于**控制面**：客户端经 HTTPS 请求自建服务；战斗属于**数据面**：客户端经 Unity Transport/UDP 直连 Unity Linux Dedicated Server。控制面不转发逐 Tick 战斗数据。
2. Dedicated Server 保存唯一的权威战局并独立推进 Tick；客户端提交输入，依据服务器状态渲染。服务器没收到输入时，**不能预知玩家按了什么**。
3. 客户端可以立即预测自己的移动，但命中、伤害、怪物 AI、波次、任务和结算由服务器裁定；收到服务器状态后，客户端还要校正**自己的**预测，并非只更新怪物和队友。
4. 网络问题不必然降低本机画面 FPS，却可能造成实体位置停顿、延迟或回拉。延迟、抖动、丢包、服务器 Tick 耗时和客户端插值设计都重要。
5. 当前项目“输入发送一次后停住”的**代码级原因之一**是输入 Tick 被最近收到的服务端 Tick 限制为最多超前 1；快照停更后，输入驱动会暂停提交。它不等于已证明网络最初为何停更，也不等于底层所有 UDP 包都停止。

## 一、今晚的问题，按一场游戏的顺序重看

### 1. 注册、建房和开局分别连接谁？

旧方案曾依赖 Unity Authentication/Multiplayer 服务，因此有些网络上注册需要境外代理。当前工作区正在转向自建 HTTPS 账号与房间控制面：账号、令牌和房间状态由服务端管理，数据库用于持久化，房主开局后由控制面分配 Dedicated Server 并发放入局票据。客户端据此连接游戏服务器的公网地址和 UDP 端口。Unity Netcode for GameObjects（NGO）和 Unity Transport 仍作为通信库；**使用 Unity 的通信库不等于战斗流量经过 Unity 云服务**。旧 Unity 账号密码无法直接取出，切换自建账号后需要重新注册或另做账号关联。

同一台腾讯云主机可以同时运行控制面和战斗进程，但它们仍是不同职责的服务。将来迁移时，应通过稳定的 HTTPS API、可配置地址、独立数据库目录和备份流程切换，而不是把客户端写死为某台主机。当前工作区的自建控制面代码与部署说明仍在变动，**是否已在公网完整部署、备份恢复是否通过验收，需另看对应测试记录**。

### 2. 服务器返回的是画面吗？客户端还计算什么？

服务器运行规则，不传视频帧：它决定玩家合法位置、碰撞、射击命中、生命、怪物、波次、掉落和任务结果，并复制状态或事件。客户端使用本地模型、动画、音频、UI 和特效渲染；立即预测本地玩家已经提交的输入；平滑显示收到的队友和怪物状态。显示上的预测不是伤害或任务完成的最终裁定。

### 3. “服务端与客户端两套 Tick”是校对真实时钟吗？

不是。服务端 Tick 是世界仿真的固定步编号；客户端命令也带一个单调递增的输入 Tick 和序列号，以便排序、校验与确认。它们不是两台机器的墙上时间，也不是“发一条、等专属回执、再发一条”的 HTTP 请求模型。服务端没有输入仍按自己的固定步推进世界和发布状态。

当前输入驱动的 `HasServerTickBudget()` 用**最近收到的** `WorldState.ServerTick + MaximumFutureCommandTicks` 限制下一条输入；未来窗口目前为 1 Tick。若客户端最近看到服务端 Tick 100，可以提交标记 101 的输入，之后必须先看到更高的服务端 Tick 才能继续。这与“服务端接受多旧的命令”是两项不同规则：正式战局在 60 Tick/s 下的过去窗口为 `max(12, ceil(60 × 0.5)) = 30 Tick`，约 0.5 秒。稳定到达的快照可以形成持续流水线；快照停更则会耗尽 1 Tick 额度。

### 4. 服务端尚未收到 W，玩家和怪物如何演算？

服务端**不知道**尚未到达的 W。在当前实现中，它会继续推进敌人和任务，但无玩家命令时保留玩家上次的权威位置。收到合法的迟到命令后，才按该命令与上次客户端命令的 Tick 差积分玩家移动；既往敌人 AI 和伤害不会整体倒带重演。

下面把用户的例子固定为“此前没有新的移动命令，服务端第 6 Tick 才收到一条标记为客户端第 1 Tick 的前进命令”；怪物每 Tick 前进 1 m 只是便于理解的假设，并非项目实际速度：

| 时刻 | 服务端知道什么、做什么 | 客户端可能显示什么 |
| --- | --- | --- |
| 客户端按下 W | 输入已发出，但服务端尚未知晓 | 对已提交的输入立刻预测本地移动 |
| 服务端 Tick 1～5 | 玩家保持旧权威位置；怪物基于当时的世界状态继续行动 | 依据陆续收到的旧快照显示怪物 |
| 服务端 Tick 6 | 当前代码**先更新敌人，再处理本 Tick 收到的命令**；若是首次命令，玩家此时只按 1 Tick 的移动量更新 | 待 Tick 6 状态到达后校正本地玩家、显示新的怪物状态 |

返回的是 **Tick 6 的当前权威世界状态**，不是“怪物只走了 1 m 时”的旧状态。此前怪物依据旧玩家位置走的路不会被自动改写；如果当时发生伤害，也不能假设迟到移动会撤销它。那些 Tick 并非白算，而是服务器已经采用的历史，只是与玩家真实按键时刻可能有偏差。若后续命令跳过多个输入 Tick，当前积分会用**这条新命令的输入值**近似覆盖缺口；它不是把缺失的每条历史输入准确重建。代码另有射击历史取样，不能把它误认为“整场世界会回滚”。

### 5. 客户端在等待状态包的 1～7 Tick，怪物会不会自己追玩家？

不会运行另一份权威怪物 AI。服务端即使没收到玩家输入，也会继续发布自己的 Tick 状态；正常情况下客户端在第 8 Tick 收到“服务端第 6 Tick 状态”之前，可能已陆续收到更早的状态。怪物表现脚本读取最新权威目标位置，逐帧向它 `Lerp`；如果新状态长期不到，只能接近最后已知位置并停在那里，不能准确续算它的决策。**其他玩家已经有带 Tick 的短快照插值缓冲**，怪物目前没有同等的时间线缓冲；因此第三项改造主要针对怪物，并统一两类远端实体在抖动下的策略。

### 6. 网络越快，画面 FPS 就越高吗？

不是同一个指标。客户端可继续以本机帧率渲染相机、UI、动画和静态场景；网络状态包间隔不稳时，怪物即使在 60 FPS 画面里也可能“走—停—跳”。稳定但稍大的延迟可以通过插值换取较平滑、略滞后的表现；抖动、丢包和服务器追不上 Tick 通常更难掩盖。更低延迟有用，但**只追求提高 Tick 率或更快发包，不会自动修复输入门限和不连续的快照**。

### 7. 为什么观察到客户端发一次后停止？到底是哪一方向坏了？

已能从代码解释一条应用层停发路径：输入驱动发送到“最新收到的服务端 Tick + 1”后，若下行快照不再前进，`HasServerTickBudget()` 返回 false，移动/射击输入 RPC 不再提交，连本地预测也不能按该驱动无限继续。此前公网测试曾观察到客户端早期收到过服务端快照，后来 Tick 停更并断线；这只证明**早期回程到达过**，不能证明后续服务端包成功抵达，也不能单凭发送字节数认定收端已收到。

诊断必须同时记录：客户端输入采样数/提交数/命令 Tick、最近完整快照 Tick、双方传输层实际收发字节、服务器接受/拒绝命令数、连接状态与断线原因。先找最早停下的是客户端应用提交、客户端 UDP 发出、服务器收到、服务器发布，还是客户端收到。校园网、代理路由和服务端回程都可能影响链路；“服务端发送计数增加”不能替代客户端接收证据。

## 二、当前代码真实边界

| 能力 | 当前状态 | 不应误解为 |
| --- | --- | --- |
| 服务端固定步仿真 | 已实现；无输入也 `ServerStep()`，更新敌人并发布权威状态 | 缺输入时已准确模拟真实玩家按键 |
| 本地玩家预测/校正 | 已实现；提交输入时预测，收到权威状态后移除已确认命令、重放未确认命令 | 快照停更时仍无限采样和预测 |
| 其他玩家位置显示 | 已有带 Tick 的 `RemoteSnapshotInterpolator`，默认约 2 Tick 展示延迟 | 怪物也使用了相同插值缓冲 |
| 怪物位置显示 | 当前逐帧 `Lerp` 到最新复制目标位置 | 已按两个真实快照的服务端时间线插值 |

| 自建账号/房间 | 工作区已有自建 HTTPS/SQLite 控制面改造 | 已凭文档证明正式公网包和完整对局验收通过 |

## 三、下一步三个改造方向：原理、收益、代价和验收

下面是**拟实施的设计**，不是说这些功能都已经完成。三项相互配合，但第一目标应先解除“快照一停，输入也停”的耦合，再证明客户端和服务端能持续交互到战局结束。

### 方向 A：客户端独立输入采样、持续发送与本地预测

**原理。** 按本地固定节奏采样输入，生成单调递增的命令序列和客户端输入 Tick，不把“是否收到新快照”作为发送的直接开关。客户端保留一小段未确认命令，立即按同一移动规则预测自身表现；服务端状态携带已处理的命令序列，客户端丢弃已确认项，并从权威位置重放余下命令。需要有界队列和失联策略：网络持续不可用时不能无限生成积压包、无限预测玩家穿过世界，应及时告警、暂停/限时预测并重连或结束会话。

**优势。** 短暂下行抖动不再直接切断上行输入；本地操作响应不必等完整往返；服务器恢复更新后仍可用确认序列对齐。现有预测/重放类可复用，但输入 Tick 生成、额度判定和状态机需要改。

**代价与风险。** 客户端 Tick 与服务端 Tick 要建立受控映射，不能简单“把未来窗口从 1 调到很大”；否则合法输入可能被服务端当成超前命令拒绝。长时间丢包时预测误差、队列内存、动作重复触发都需上限。当前移动、跳跃、开火共用可靠有序流；若改传输类型，必须先设计跨通道顺序、离散动作去重和丢包恢复，不能直接把所有 RPC 改成不可靠。

**验收指标。** 在可控下行短暂停更期间，客户端“采样数”持续增加，应用层“提交数”按所定策略持续且有界，命令序列无重复/倒退；恢复后已确认序列推进，未确认队列收敛，预测校正次数和最大误差有记录；长期断线能明确超时而非静默积压。

### 方向 B：服务端短输入队列与缺失输入策略

**原理。** 按玩家保存经身份验证、按序号和 Tick 排列的短命令队列，在固定服务端 Tick 中消费适当的客户端输入。要估计客户端输入时序与服务端 Tick 的映射，并给网络抖动留小而可测的缓冲。短时缺失移动输入时，可有限度地沿用最后已知的持续按键，或采取保守停止；**跳跃、开火、拾取等一次性动作不能凭空重复预测**。迟到包到达后校验并更新未来状态；若不实现完整回滚，就明确接受之前 AI 轨迹已发生，并用权威快照校正客户端。

**优势。** 服务端不会因为单个包晚到就必须把多个客户端时间步集中在一个世界 Tick 内处理；较小的抖动可被队列吸收，玩家移动与敌人感知的时序更一致；诊断时能看见队列积压、缺失、迟到和拒绝的各自比例。

**代价与风险。** 多缓冲 1 Tick 就多一点输入延迟，缓冲太短则频繁预测/校正。沿用上一移动键可能在玩家已松手时继续移动，必须设置很短的缺失上限和碰撞/速度校验；不能为了一致性牺牲防作弊。射击历史补偿与世界回滚是不同问题；未来若要求完整历史重算，复杂度与内存成本会显著增加，不应在本轮承诺。

**验收指标。** 记录每玩家输入到达延迟（按 Tick）、队列长度、缺失 Tick、预测 Tick、迟到/过期/超前拒绝次数、服务器 Tick 耗时。模拟稳定延迟、抖动和少量丢包时，服务器保持固定步推进，持续接受合法命令，不产生无界队列或重复开火；断线时能安全收束。

### 方向 C：带 Tick 的状态缓冲与远端实体插值

**原理。** 客户端保存最近若干个带服务端 Tick 的权威快照，把“展示时间”故意放在已知最新 Tick 之前一小段距离。例如已有 Tick 100 与 102，展示 Tick 101 时按两端位置、朝向插值，而不是每帧追赶 Tick 102 的目标点。其他玩家已有相应的短缓冲；主要需把怪物显示改为同类时间线，并处理生成、死亡、瞬移、换场和长期缺包：这些事件不能盲目插值；快照耗尽时保守保持或极短外推，不在客户端擅自运行怪物 AI。

**优势。** 快照到达间隔不匀时，远端运动仍能按服务端时间顺序平滑显示；怪物和队友的视觉规则一致；单个迟到/乱序快照更容易识别和丢弃。

**代价与风险。** 展示会主动落后约若干 Tick，缓冲越长越顺滑但越“旧”；需避免把视觉位置误用于服务器伤害判定，重要事件要与对应的 Tick/实体代数对齐。持续断线无法靠插值凭空补出正确轨迹。

**验收指标。** 记录快照到达间隔、插值缓冲占用、无可插值样本的帧数、可见位置跳变距离，以及端到端展示延迟；在相同模拟链路下与旧版 `Lerp` 比较。生成/死亡/瞬移无拖影，长期缺包不会让怪物无限外推。

## 四、如何判定这轮优化真的解决问题

1. **先复现并测量，而非只看“感觉流畅”。** 两端同步采集发送与接收字节、输入采样/提交/接受数、命令序号、快照 Tick、连接状态、断线原因；保留无需打印密钥或票据的日志。对比无延迟、固定延迟、抖动和丢包几种情形。
2. **最小目标是不断流。** 单客户端、双客户端均能从进入 CityNew 到三波、终端、撤离和结算持续发送输入并接收权威状态；不能只在前几十个 Tick 成功。若网络真正中断，客户端要明确超时或重连，不得表面上仍在对局却静默停止提交。
3. **再看正确性和体验。** 移动、跳跃、射击不能重复或漏算；服务端权威生命、怪物、背包和任务状态在两端一致；预测回拉、怪物跳变、输入队列峰值与服务器 Tick 耗时要可量化，并与优化前同网络条件比较。
4. **区分测试层级。** 纯逻辑单元测试和同机多进程测试不能替代真实公网双客户端验收；控制面 HTTPS 正常也不能替代战斗 UDP 全流程验收。
